# Синхронизация Known Issues с GitHub Issues

**Статус документа:** проектная спецификация
**Дата:** 2026-10-19
**Целевой файл:** `scripts/sync-known-issues.ps1`
**Источник истины:** [KNOWN_ISSUES.md](KNOWN_ISSUES.md)

> **Скрипт ещё не реализован.** Каталога `scripts/` в репозитории нет;
> документ фиксирует дизайн, чтобы реализация не меняла формат реестра задним
> числом. Отсутствие скрипта зарегистрировано как KI-010 (🟢 Low, Deferred).

## 1. Назначение

Скрипт `scripts/sync-known-issues.ps1` выгружает записи `KI-XXX` из
`docs/KNOWN_ISSUES.md` в GitHub Issues репозитория, чтобы:

- проблемы проекта были видны внешним пользователям без доступа к реестру;
- по KI можно было фильтровать и подписываться средствами GitHub;
- не дублировать данные вручную: реестр остаётся единственным источником
  истины, Issues — его зеркало.

Скрипт не заменяет баг-трекер и не является двусторонним: изменения в Issues
не переносятся обратно в Markdown.

## 2. Принципы

1. **Односторонняя синхронизация** — только `docs/KNOWN_ISSUES.md` →
   GitHub Issues.
2. **Идемпотентность** — повторный запуск без изменений в реестре не создаёт
   дублей и не меняет Issues.
3. **Dry-run обязателен для первого запуска** — сначала `-DryRun`, затем
   реальная запись после просмотра плана.
4. **Никаких удалений** — Issues не удаляются и не закрываются автоматически
   (закрытие — только явный флаг `-CloseFixed`).
5. **Идентичность по маркеру** — Issue связывается с KI скрытым HTML-маркером
   в теле, а не только заголовком: заголовок можно переименовать, маркер —
   нет.
6. **Секреты не попадают в командную строку и логи** — токен читается из
   переменной окружения.

## 3. Схема работы

```text
docs/KNOWN_ISSUES.md
        │  парсинг + валидация
        ▼
   [модель KI]  ──► сравнение с существующими Issues (GET)
        │                         │
        │                         ├─ нет маркера  → CREATE
        │                         ├─ маркер есть  → UPDATE (если изменилось)
        │                         └─ совпадает    → SKIP
        ▼
  GitHub REST API v3 (api.github.com)
        │
        ▼
  Issues с метками ki / priority:* / status:*
```

## 4. Входной формат и правила парсинга

Скрипт разбирает только секции, созданные по шаблону реестра.

- Секции версий `## vX.Y.Z — …` используются как справочные, но не
  синхронизируются отдельными Issues.
- Заголовок записи (H3), обязательный формат с длинным тире:

```text
### KI-002 — POST /v1/chat/completions отвечает заглушкой 501 (Open)
```

- Регулярное выражение заголовка (эм-дефис `—`, U+2014):

```powershell
$h3Pattern = '^### (KI-\d{3}) — (.+?) \((Open|In Progress|Fixed|Documented|Deferred|Won''t Fix)\)$'
```

- Поля записи — фрагменты `**Название поля:** значение`. Одна строка может
  содержать несколько полей через разделитель ` | ` (так оформлена строка
  приоритета/статуса в реестре):

```text
- **Приоритет:** 🟠 High | **Статус:** Open | **Обнаружено:** 2026-10-19
```

  Парсер разбивает строку по ` | `, сегменты, начинающиеся с `**`,
  трактует как отдельные поля, а остальные присоединяет к значению
  предыдущего поля. Это позволяет добавлять новые поля без изменения
  скрипта.
- Поддерживаются как минимум поля `Приоритет`, `Файлы`, `Описание`,
  `Связанные`; остальные (например, `Влияние`, `План`, `Обходной путь`)
  переносятся в тело Issue без интерпретации.
- Многострочное значение поля продолжается до следующей строки
  `- **…:**`, следующего `###` или `##`; пустая строка завершает только
  текущий абзац значения.
- Из заголовка берутся `id`, `title` и `status`; из поля `Приоритет` —
  уровень (`🔴 Critical` → `critical` и т.д.). Поле `Статус` в строке полей
  должно совпадать со статусом в заголовке (заголовок — источник истины;
  расхождение — ошибка валидации, код 4). Неизвестный статус/приоритет —
  ошибка валидации (код 4), Issue не создаётся.
- Повторяющийся `id` в реестре — ошибка валидации (код 4); скрипт ничего не
  пишет, пока реестр не исправлен.

## 5. Метки (labels)

Скрипт обеспечивает существование меток (создаёт отсутствующие) и навешивает
на каждый Issue ровно три группы меток: `ki`, одна `priority:*`, одна
`status:*`. Старые метки этих групп удаляются при обновлении.

| Метка | Цвет | Описание |
|---|---|---|
| `ki` | `5319e7` | Запись реестра известных проблем |
| `priority:critical` | `b60205` | 🔴 Critical |
| `priority:high` | `d93f0b` | 🟠 High |
| `priority:medium` | `fbca04` | 🟡 Medium |
| `priority:low` | `0e8a16` | 🟢 Low |
| `status:open` | `d4c5f9` | Open |
| `status:in-progress` | `c2e0c6` | In Progress |
| `status:fixed` | `1d76db` | Fixed |
| `status:documented` | `bfd4f2` | Documented |
| `status:deferred` | `ededed` | Deferred |
| `status:wontfix` | `e6e6e6` | Won't Fix |

Создание меток — отдельный шаг; при `-DryRun` он только печатается
(`[ENSURE-LABEL] priority:critical`) и не выполняется. Ошибка «метка уже
существует» (`422`) игнорируется.

## 6. Идемпотентный upsert

Алгоритм для каждого KI из реестра:

1. Сформировать желаемые значения:
   - `title`: `[KI-002] POST /v1/chat/completions отвечает заглушкой 501`;
   - `body`: детерминированный Markdown (см. шаблон ниже) с маркером
     `<!-- ki-id: KI-002 -->` в первой строке;
   - `labels`: `ki`, `priority:<...>`, `status:<...>`.
2. Найти существующий Issue:
   - получить все Issues репозитория с меткой `ki`
     (`GET /repos/{owner}/{repo}/issues?state=all&labels=ki&per_page=100`,
     постранично);
   - сопоставить по маркеру `ki-id`; fallback — по префиксу заголовка
     `[KI-002]`; если найдено два Issue с одним маркером — остановиться с
     кодом 5 (ручное разрешение).
3. Сравнить текущие `title`, нормализованное `body` (CRLF → LF) и набор меток
   с желаемыми:
   - нет Issue → **CREATE** (`POST /repos/{owner}/{repo}/issues`);
   - есть, но отличается → **UPDATE** (`PATCH /repos/{owner}/{repo}/issues/{number}`);
   - совпадает → **SKIP** (запросов на запись нет).
4. Если Issue закрыт, а KI снова `Open`/`In Progress` — Issue переоткрывается
   (`PATCH` с `state: "open"`) и добавляется комментарий о причине.
5. Если `-CloseFixed` и статус `Fixed`/`Won't Fix` — Issue закрывается с
   комментарием; без флага статус меняется только в метках.

Тело Issue строится детерминированно, чтобы повторная синхронизация без
изменений давала идентичный текст:

```markdown
<!-- ki-id: KI-002 -->
> Синхронизировано из `docs/KNOWN_ISSUES.md` (реестр 0.1.0, 2026-10-19).
> Источник истины — реестр; ручные правки будут перезаписаны.

## KI-002 — POST /v1/chat/completions отвечает заглушкой 501

- **Приоритет:** 🟠 High
- **Статус:** Open
- **Файлы:** `src/index.ts`, `docs/DESIGN.md` § 7
- **Описание:** …текст из реестра…
- **Связанные:** KI-003, KI-004, KI-005, KI-006

---
Автосинхронизация: `scripts/sync-known-issues.ps1` (односторонняя).
```

## 7. Параметры командной строки

| Параметр | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `-Repo` | `string` | — (обязателен) | `owner/repo`, куда синхронизировать |
| `-KnownIssuesPath` | `string` | `docs/KNOWN_ISSUES.md` | Путь к реестру |
| `-DryRun` | `switch` | выключен | Показать план, не выполняя запись |
| `-TokenEnvVar` | `string` | `GITHUB_TOKEN` | Имя переменной окружения с токеном |
| `-ApiBaseUrl` | `string` | `https://api.github.com` | Для GitHub Enterprise Server |
| `-CloseFixed` | `switch` | выключен | Закрывать Issues для `Fixed`/`Won't Fix` |
| `-Verbose` | `switch` | выключен | Подробный лог (без секретов) |

Пример вызова (порядок параметров не важен):

```powershell
pwsh -NoProfile -File .\scripts\sync-known-issues.ps1 `
    -Repo 'owner/ai-dsh-bridge' `
    -KnownIssuesPath 'docs/KNOWN_ISSUES.md' `
    -DryRun
```

## 8. Токен, права и лимиты

- Токен читается **только** из переменной окружения, имя которой задаёт
  `-TokenEnvVar`; передача токена параметром командной строки запрещена
  (утекает в историю и список процессов).
- Минимальные права **fine-grained PAT**: `Issues: Read and write`,
  `Metadata: Read`. Для приватного репозитория этого достаточно.
- Классический PAT: `public_repo` — для публичного репозитория, `repo` — для
  приватного.
- В GitHub Actions — `GITHUB_TOKEN` с `permissions: issues: write,
  contents: read`.
- Лимиты API: 5000 запросов/час с токеном (60/час без токена). Скрипт делает
  один листинг + по одному запросу на каждое расхождение; при `403`/`429` с
  `x-ratelimit-remaining: 0` ожидает до `x-ratelimit-reset` (не более 60 с),
  иначе завершается с кодом 3.
- Токен маскируется в выводе (`ghp_****`) и никогда не пишется в файлы.

```powershell
# Получить токен из gh CLI в текущую сессию (не сохраняется в файл)
$env:GITHUB_TOKEN = (gh auth token)

# Либо ввести вручную без эха
$secure = Read-Host -AsSecureString 'GitHub token'
$env:GITHUB_TOKEN = [System.Net.NetworkCredential]::new('', $secure).Password
```

## 9. Запуск: сценарии

**9.1. Первый запуск — только план.**

```powershell
$env:GITHUB_TOKEN = (gh auth token)
pwsh -NoProfile -File .\scripts\sync-known-issues.ps1 -Repo 'owner/ai-dsh-bridge' -DryRun
```

**9.2. Реальная синхронизация после проверки плана.**

```powershell
pwsh -NoProfile -File .\scripts\sync-known-issues.ps1 -Repo 'owner/ai-dsh-bridge'
```

**9.3. GitHub Actions (workflow_dispatch + изменения реестра).**

```yaml
name: sync-known-issues
on:
  workflow_dispatch:
  push:
    branches: [main]
    paths: ['docs/KNOWN_ISSUES.md']
permissions:
  contents: read
  issues: write
jobs:
  sync:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: Sync KI to GitHub Issues
        shell: pwsh
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: ./scripts/sync-known-issues.ps1 -Repo ${{ github.repository }}
```

## 11. Коды возврата

| Код | Значение |
|---|---|
| `0` | Успех (для `-DryRun` — успешный разбор и план; расхождения не ошибка) |
| `1` | Ошибка параметров/использования (нет `-Repo`, неверный путь) |
| `2` | Ошибка аутентификации: нет токена, `401`/`403` от API |
| `3` | Ошибка API/сети: `5xx`, rate limit, таймаут |
| `4` | Ошибка парсинга/валидации реестра (неизвестный статус, дубль KI) |
| `5` | Несогласованное состояние: два Issue с одним маркером `ki-id` |

Коды 1–5 означают, что синхронизация не выполнена; частично применённые
изменения безопасны для повторного запуска (идемпотентность).

## 12. Ограничения

- **Только одно направление.** Правки заголовка/тела Issue в GitHub
  перезаписываются при следующей синхронизации.
- **Не удаляет Issues.** Скрипт никогда не вызывает `DELETE`; закрытие —
  только `-CloseFixed`.
- **Не синхронизирует комментарии** и обсуждения; комментарии в Issue
  сохраняются, но не переносятся в реестр.
- **Не назначает** assignee, milestone, projects, не управляет `state_reason`
  сверх описанного.
- **Не переносит вложения** и изображения; вложения из Markdown-реестра
  (если появятся) в тело Issue не попадут.
- **Ручные конфликты решаются вручную.** Если Issue правили в GitHub, а
  реестр — локально, побеждает реестр (last write wins); потерянные правки
  фиксируются только в истории Issue.
- **Строгий формат обязателен.** Заголовки и поля не по шаблону KI игнорируются
  или приводят к ошибке 4; свободный Markdown внутри реестра без записи
  `### KI-XXX` не синхронизируется.
- **Не синхронизирует CHANGELOG и версии** — только записи KI.
- **Лимиты API и пагинация.** Более 1000 Issues с меткой `ki` (10 страниц по
  100) — ошибка 3: требуется ручная оптимизация/GraphQL.
- **`-DryRun` не полностью офлайн**: листинг существующих Issues читается
  через API; для приватного репозитория токен нужен даже в режиме плана.
- **Только `pwsh` 7+.** На Linux/macOS скрипт запускается через PowerShell 7,
  зависимости от Windows-команд нет, но `powershell.exe` 5.1 не
  поддерживается.
- **Не заменяет GitHub Projects/трекер** и не строит отчёты.

## 13. Безопасность

- Токен не логируется и не передаётся аргументами; в выводе маскируется.
- Все запросы — только по HTTPS (`-ApiBaseUrl` для GHES должен быть https).
- Скрипт не читает `~/.ai-dsh-bridge/auth.json` и файлы сессии DeepSeek.
- `-DryRun` не выполняет `POST`/`PATCH`/`DELETE`; единственные запросы —
  `GET` списка Issues и `GET` меток.
- Запуск в CI ограничен `issues: write`; права на код не требуются.

## 14. Тестирование и развитие

- Планируемые тесты (Pester 5, `scripts/tests/`): разбор реестра на
  фикстурах, маппинг приоритетов/статусов, dry-run без записи, идемпотентный
  повтор (mock `Invoke-RestMethod`), ошибки валидации (код 4), дубли маркера
  (код 5).
- Будущее развитие: запуск по расписанию, опциональный GraphQL-листинг для
  больших репозиториев, перенос ссылок на коммиты из `CHANGELOG` в Issue.
- Скрипт и тесты появятся после стабилизации формата реестра (KI-010);
  изменения формата KI обязаны сопровождаться обновлением этого документа и
  CHANGELOG.
