## 1. Контекст: зачем агенту зрение

### 1.1. Проблема

Сейчас агент (DSH) может выполнить `bash`, управлять мышью и сохранять
файлы, но **не видит содержимое экрана и изображений**. Типичные задачи,
которые без этого не решаются:

- проанализировать интерфейс приложения и найти элемент;
- прочитать текст со скриншота или скана PDF (в т.ч. таблицы, формы);
- проверить результат собственного действия (открылось ли окно, что
  изображено на скриншоте);
- ответить на вопрос по картинке, которую пользователь приложил к чату.

DeepSeek Web API, который использует шлюз, принимает только текстовый
`prompt`. Прямого канала «картинка → модель» в текущем транспорте нет:
`ref_file_ids` в захваченных запросах относится к файлам, а не к
изображениям для vision, и его поведение для изображений не подтверждено.

### 1.2. Что уже есть

- `bash` как универсальный инструмент: можно запустить Python/PowerShell,
  сохранить скриншот в файл и вернуть путь.
- Prompt Builder: единственное место, где формируется текст запроса;
  сюда можно добавить результат распознавания.
- Клиент DeepSeek и SSE-слой: не меняются, если изображение превращается
  в текст **до** отправки.
- `screenshot`-инструмента пока нет (R-06-04) — сейчас скриншот делается
  скриптом через `bash`, результат виден модели только как путь.

### 1.3. Цели и нецели

**Цели v0.6.0:**

- получить текст/описание изображения локально и передать его в `prompt`;
- поддержать сценарий «скриншот → распознавание → ответ пользователю»;
- не отправлять изображения и секреты с экрана во внешние сервисы без
  явного согласия.

**Нецели:**

- потоковая передача изображений в DeepSeek (зависит от внешнего API);
- обучение/дообучение собственной vision-модели;
- замена OCR на полноценное понимание сцены во всех случаях.

## 2. Ключевое архитектурное решение: как передавать картинки в модель

### 2.1. Варианты

#### Вариант A — OCR через `bash` (Tesseract)

**Поток:** модель вызывает `bash` → `tesseract screenshot.png stdout` →
текст возвращается как `tool`-результат → следующий turn отвечает по тексту.

- **Плюсы:** не нужен GPU; работает локально; быстро (сотни мс на
  скриншот); не требует изменений клиента DeepSeek; легко тестируется на
  фикстурах.
- **Минусы:** только текст; плохо с иконками, схемами, сложной вёрсткой;
  качество зависит от разрешения и шрифтов; нужен установленный Tesseract
  и языковые пакеты (`rus`, `eng`).

#### Вариант B — локальная vision-модель (Ollama/LLaVA)

**Поток:** `screenshot` сохраняет PNG → шлюз делает HTTP-запрос к
локальному Ollama (`/api/generate` с base64) → описание возвращается
модели как текст `tool`-результата.

- **Плюсы:** понимает сцену, иконки, вёрстку; описание можно дать модели
  как обычный текст; полностью локально (приватность).
- **Минусы:** нужны GPU/память (единицы ГБ), модель надо скачать;
  задержка секунды; качество зависит от модели; дополнительная
  зависимость и конфигурация (URL, таймаут, размер изображения).

#### Вариант C — CDP-fallback / родная поддержка DeepSeek Web

**Поток:** если DeepSeek Web API начнёт принимать изображения
(`ref_file_ids`/multimodal-поле), шлюз передаёт base64 через CDP или
прямой HTTP, а модель видит картинку нативно.

- **Плюсы:** лучшее качество (модель видит оригинал), нет локальных
  моделей.
- **Минусы:** зависит от внешнего API и его стабильности; CDP-транспорт
  хрупок (селекторы, WAF, версии интерфейса); требует перехвата
  внутреннего запроса; приватность (изображение уходит в DeepSeek);
  сейчас нет подтверждения, что API это поддерживает.

### 2.2. Сравнение

| Критерий | A: OCR | B: LLaVA | C: CDP/native |
|---|---|---|---|
| Понимание сцены | низкое (только текст) | высокое | высокое |
| Задержка | ~0.2–1 с | ~2–10 с | зависит от DeepSeek |
| Железо | CPU | GPU/память | CPU + Chrome |
| Приватность | локально | локально | уходит в DeepSeek |
| Внешняя зависимость | Tesseract | Ollama + модель | DeepSeek API/WAF |
| Сложность | низкая | средняя | высокая |
| Риск поломки | низкий | средний | высокий |

### 2.3. Выбор: гибрид A → B (C отложен)

Выбираем **гибридную схему**:

1. **Сначала OCR (A).** Для большинства задач достаточно текста:
   прочитать сообщение об ошибке, найти подпись, распознать форму.
   Дешёво, быстро, локально.
2. **Если OCR не хватает — LLaVA (B).** Когда нужен смысл сцены
   (иконки, расположение элементов, «что изображено»), шлюз вызывает
   локальную vision-модель и получает описание.
3. **CDP/native (C) — Deferred** (R-06-03): включаем только если DeepSeek
   официально поддержит изображения и это подтвердится живым захватом.

Схема сохраняет главное преимущество текущей архитектуры: **DeepSeek
продолжает получать только текст**, поэтому клиент, PoW и SSE-слой не
меняются.

### 2.4. Поток данных (эскиз)

```text
DSH → POST /v1/chat/completions (tools=[screenshot, bash])
  → Prompt Builder (инструкция: для изображения используй screenshot)
  → DeepSeek: DSML tool_calls (screenshot / bash)
  → шлюз выполняет инструмент (или DSH — в зависимости от роли tools)
  → файл PNG на диске
  → выбор: OCR (tesseract) или LLaVA (Ollama) — по типу задачи/настройке
  → текст/описание как tool-результат
  → следующий turn DeepSeek отвечает пользователю
```

Точки интеграции: `R-06-04` (инструмент `screenshot`), Prompt Builder
(инструкция «сначала OCR, если текст; иначе описание»), конфиг шлюза
(URL Ollama, языки OCR, таймауты), `tool`-сообщения истории.

### 2.5. Fail-safe и приватность

- Если OCR/LLaVA недоступны — не падать, а вернуть понятную ошибку
  инструмента; модель должна ответить текстом с причиной.
- Скриншоты не логируются и не попадают в `docs/captures/`; временные
  файлы удаляются после обработки.
- LLaVA вызывается только по явной настройке (`VISION_PROVIDER=ollama`);
  по умолчанию — OCR или отказ.
- Изображения с экрана могут содержать токены/переписку: запрос к
  внешним сервисам (вариант C) запрещён без отдельного согласия.

### 2.6. Открытые вопросы

- Как DSH передаёт изображения в запросе — как `content`-часть или через
  инструмент? От этого зависит, нужен ли R-06-04 вообще.
- Поддерживает ли DeepSeek `ref_file_ids` для изображений (R-06-03)?
- Минимально достаточное разрешение/формат для OCR и LLaVA.
- Нужны ли языковые пакеты `rus` в базовой поставке.
- Где брать Ollama в Docker-образе (отдельный контейнер или host).

## 3. Технические срезы

> Ниже — архитектура и интерфейсы, не реализация. Код появится в шагах
> S1–S5 (§ 4). Шлюз **не выполняет инструменты**: их выполняет DSH, шлюз
> только транслирует `tools`/`tool_calls` и текст. Поэтому «инструмент
> `screenshot`» — это CLI/MCP-инструмент, доступный DSH (через `bash` или
> MCP), а не HTTP-эндпоинт шлюза.

### 3.1. Инструмент `screenshot`

**Назначение.** Сделать скриншот экрана/монитора/области и вернуть модели
путь к файлу (и, при необходимости, base64 для локального vision-адаптера).

**Реализация.** Node.js-обёртка над `screenshot-desktop` (кроссплатформенно:
Windows GDI, macOS `screencapture`, Linux X11/Wayland-ограничения).
Альтернатива — `screenshot` (проще, меньше контроля). Обёртка
`scripts/screenshot.mjs` + MCP-адаптер `@deepseek-ai/dsh-tool-screenshot`
(если DSH-профиль поддерживает MCP) — выбирается на S1.

**Вход:**

```ts
interface ScreenshotInput {
  monitor?: string;                 // id/индекс монитора; по умолчанию основной
  region?: { x: number; y: number; width: number; height: number };
  format?: 'png';                   // v0.6.0: только PNG
}
```

**Выход (JSON в `tool`-результат):**

```ts
interface ScreenshotResult {
  base64: string;                   // PNG в base64 (для локального vision)
  filePath: string;                 // абсолютный путь к сохранённому PNG
  mimeType: 'image/png';
  width: number;
  height: number;
  bytes: number;
}
```

**Куда сохранять.** Приоритет: `data/screenshots/` внутри cwd сессии
(который передаёт DSH), имя `<YYYY-MM-DD-HH-mm-ss>-<pid>.png`; если cwd
недоступен — `os.tmpdir()/ai-dsh-bridge/screenshots/`. Файл удаляется
после успешной обработки OCR/LLaVA (или по TTL).

**Важно:** base64 **не вставляется в prompt** — это раздувает токены и
может превысить лимиты. Модели передаётся `filePath` и метаданные; base64
использует только локальный адаптер (LLaVA/OCR) или CDP-загрузка.

**Ошибки:** нет дисплея/доступа к экрану (headless, Wayland), нет прав,
диск переполнен — возвращать структурированную ошибку инструмента, не
бросать необработанное исключение.

### 3.2. OCR через Tesseract

**Назначение.** Быстрый текстовый fallback: скриншот → текст.

**Варианты:**

- **Bash + системный Tesseract (предпочтительно):**
  `tesseract screenshot.png stdout -l rus+eng --psm 6`. Плюсы: без
  Node-зависимостей, языки ставятся отдельно, быстрее WASM. Минусы: нужен
  установленный бинарник и traineddata; на чистой машине — дополнительный
  шаг установки.
- **`tesseract.js` (WASM):** не требует системного бинарника, но медленнее,
  языковые данные грузятся отдельно, качество на сложных шрифтах ниже.

**Инструмент `ocr`** (CLI/MCP) или `bash`-вызов:

```ts
interface OcrInput {
  filePath?: string;                // путь к PNG/JPEG
  base64?: string;                  // альтернатива пути (локально)
  languages?: string[];             // ['rus','eng'] по умолчанию из OCR_LANG
}
interface OcrResult {
  text: string;
  confidence?: number;              // если доступно
  language: string;
}
```

**Ограничения:** только текст; не понимает иконки/вёрстку; качество падает
на мелком шрифте и тёмной теме; PDF-сканы нужно предварительно
растеризовать (вне v0.6.0). Таймаут — 30 с, лимит изображения — 10 МБ.

### 3.3. Передача картинок в DeepSeek Web

**Вариант A — `ref_file_ids` (если поддерживается).**
Проверить живым захватом: загрузить PNG через `/api/v0/file/upload_file`
(возможно, PoW challenge с `target_path` этого эндпоинта), получить id и
передать в `/chat/completion` как `ref_file_ids`; посмотреть, видит ли
модель изображение. Если да — это лучший путь: без локальных моделей,
оригинал у DeepSeek. Риски: недокументированный API, привязка к аккаунту,
возможные изменения. Если нет — зафиксировать отрицательный результат в
KNOWN_ISSUES и закрыть S3 как «не поддерживается».

**Вариант B — CDP-fallback.**
Выполнить запрос из уже авторизованной вкладки браузера, где файл
загружен штатным UI DeepSeek. Плюс: родной путь DeepSeek. Минусы: хрупко
(селекторы, WAF, версии UI), медленно, сложно тестировать; относится к
R-09-01 и в v0.6.0 не реализуется, только резервируется.

**Вариант C — локальная LLaVA через Ollama.**
Не зависит от DeepSeek: шлюз/DSH делает HTTP к `http://127.0.0.1:11434`
(`/api/generate`, base64 или путь), получает текст-описание и передаёт его
модели как `tool`-результат. Плюсы: полное описание сцены, приватность.
Минусы: GPU/память, задержка 2–10 с, качество модели.

**Выбор:** A, если подтвердится; иначе C. B — только как аварийный
резерв (v0.9.0).

### 3.4. Изменения в Prompt Builder

Сейчас `OpenAiMessage.content` — `string | null`. Vision-клиенты (DSH)
могут прислать массив частей:

```ts
type ContentPart =
  | { type: 'text'; text: string }
  | { type: 'image_url'; image_url: { url: string } }; // url = data:image/png;base64,... или https
```

**Нужно:**

1. Расширить тип/схему `content`: `string | null | ContentPart[]`.
2. При сборке prompt:
   - текстовые части склеивать в `[USER]`/`[SYSTEM]` как раньше;
   - `image_url` с data-URI: **не вставлять base64 в prompt**; сохранить во
     временный файл `data/screenshots/<hash>.png` и добавить в prompt
     строку вида `[IMAGE_SAVED path=<path> mime=image/png]`;
   - если DeepSeek поддерживает изображения (A) — передавать их через
     `ref_file_ids`, а текстовую часть строить как обычно;
   - если нет — модель получает путь и инструкцию: «если нужен текст с
     картинки — вызови OCR; если нужно описание — LLaVA» (инструкции
     добавляются в `[SYSTEM]`, как в 0.5.x).
3. `tool`-результаты со скриншотом: распознавать JSON
   `{filePath, mimeType}` (или путь в тексте) и подсказывать модели
   использовать OCR/LLaVA, а не пытаться «увидеть» файл.
4. Не логировать base64 и содержимое изображений; в логах — только путь,
   размер, mime.

**Тесты:** content-массив с text+image_url → prompt содержит текст и
`[IMAGE_SAVED]`, без base64; пустой массив → валидационная ошибка/пустой
текст; tool-результат с путём → инструкция OCR.

### 3.5. Конфигурация и лимиты

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `SCREENSHOT_DIR` | каталог скриншотов | `<cwd>/data/screenshots` |
| `OCR_LANG` | языки Tesseract | `rus+eng` |
| `OCR_TIMEOUT_MS` | таймаут OCR | `30000` |
| `VISION_PROVIDER` | `ocr` / `ollama` / `off` | `ocr` |

## 4. План работ

Оценка «сессия» — один сфокусированный рабочий шаг (код + тесты + доки),
а не календарный день.

| Шаг | Содержание | Зависимости | Результат | Сессий |
|---|---|---|---|---|
| **S1** | Инструмент `screenshot` (Node.js, без DeepSeek): CLI/MCP, сохранение PNG, `{base64,filePath,mimeType}`, тесты с mock-библиотекой | — | Модель получает путь к скриншоту | 1 |
| **S2** | OCR через `tesseract` (bash и/или tesseract.js): инструмент/инструкция, `rus+eng`, таймауты, тест на фикстуре | S1 (путь к файлу) | Текст со скриншота попадает в ответ | 1 |
| **S3** | Интеграция с DeepSeek `ref_file_ids`: живой захват загрузки PNG, проверка, поддержка в клиенте; при отказе — документированный negative result | — (внешняя) | Решение «да/нет» + код или KI | 2 |
| **S4** | Fallback на LLaVA (Ollama): HTTP-клиент, `VISION_PROVIDER=ollama`, лимиты, mock-тест | S1 (изображение) | Описание сцены без DeepSeek | 2 |
| **S5** | Тесты и документация: e2e-сценарий «скриншот → OCR/LLaVA», обновление DESIGN/ROADMAP/KNOWN_ISSUES, закрытие R-06-01/R-06-02/R-06-04 | S1–S4 | v0.6.0 готов к релизу | 1 |

**Порядок и почему:**

1. **S1 → S2:** OCR бессмыслен без стабильного способа получить PNG;
   сначала инструмент, потом распознавание.
2. **S1 → S4:** LLaVA тоже требует файл; S4 идёт после S2, потому что OCR
   дешевле и покрывает большинство случаев, а LLaVA — fallback.
3. **S3 параллелен:** проверка `ref_file_ids` — внешнее исследование, не
   блокирует S1/S2; если поддержка есть, S3 заменяет локальные модели для
   части сценариев.
4. **S5 в конце:** сквозной e2e и документация фиксируют результат и
   закрывают пункты Roadmap.

**Критерии выхода v0.6.0:** скриншот → OCR или LLaVA → ответ содержит
текст/описание; base64 не попадает в prompt; изображения не логируются;
есть mock-тесты; `ref_file_ids` исследован (поддержка подтверждена или
зафиксирован отказ).
