## 1. Контекст: зачем агенту зрение

### 1.1. Проблема

Сейчас агент (DSH) может выполнить `bash`, управлять мышью и сохранять
файлы, но **не видит содержимое экрана и изображений**. Типичные задачи,
которые без этого не решаются:

- проанализировать интерфейс приложения и найти элемент;
- прочитать текст со скриншота или скана PDF (в т.ч. таблицы, формы);
- проверить результат собственного действия (открылось ли окно, что
  изображено на скриншоте);
- ответить на вопрос по картинке, которую пользователь приложил к чату.

DeepSeek Web API, который использует шлюз, принимает только текстовый
`prompt`. Прямого канала «картинка → модель» в текущем транспорте нет:
`ref_file_ids` в захваченных запросах относится к файлам, а не к
изображениям для vision, и его поведение для изображений не подтверждено.

### 1.2. Что уже есть

- `bash` как универсальный инструмент: можно запустить Python/PowerShell,
  сохранить скриншот в файл и вернуть путь.
- Prompt Builder: единственное место, где формируется текст запроса;
  сюда можно добавить результат распознавания.
- Клиент DeepSeek и SSE-слой: не меняются, если изображение превращается
  в текст **до** отправки.
- `screenshot`-инструмента пока нет (R-06-04) — сейчас скриншот делается
  скриптом через `bash`, результат виден модели только как путь.

### 1.3. Цели и нецели

**Цели v0.6.0:**

- получить текст/описание изображения локально и передать его в `prompt`;
- поддержать сценарий «скриншот → распознавание → ответ пользователю»;
- не отправлять изображения и секреты с экрана во внешние сервисы без
  явного согласия.

**Нецели:**

- потоковая передача изображений в DeepSeek (зависит от внешнего API);
- обучение/дообучение собственной vision-модели;
- замена OCR на полноценное понимание сцены во всех случаях.

## 2. Ключевое архитектурное решение: как передавать картинки в модель

### 2.1. Варианты

#### Вариант A — OCR через `bash` (Tesseract)

**Поток:** модель вызывает `bash` → `tesseract screenshot.png stdout` →
текст возвращается как `tool`-результат → следующий turn отвечает по тексту.

- **Плюсы:** не нужен GPU; работает локально; быстро (сотни мс на
  скриншот); не требует изменений клиента DeepSeek; легко тестируется на
  фикстурах.
- **Минусы:** только текст; плохо с иконками, схемами, сложной вёрсткой;
  качество зависит от разрешения и шрифтов; нужен установленный Tesseract
  и языковые пакеты (`rus`, `eng`).

#### Вариант B — локальная vision-модель (Ollama/LLaVA)

**Поток:** `screenshot` сохраняет PNG → шлюз делает HTTP-запрос к
локальному Ollama (`/api/generate` с base64) → описание возвращается
модели как текст `tool`-результата.

- **Плюсы:** понимает сцену, иконки, вёрстку; описание можно дать модели
  как обычный текст; полностью локально (приватность).
- **Минусы:** нужны GPU/память (единицы ГБ), модель надо скачать;
  задержка секунды; качество зависит от модели; дополнительная
  зависимость и конфигурация (URL, таймаут, размер изображения).

#### Вариант C — CDP-fallback / родная поддержка DeepSeek Web

**Поток:** если DeepSeek Web API начнёт принимать изображения
(`ref_file_ids`/multimodal-поле), шлюз передаёт base64 через CDP или
прямой HTTP, а модель видит картинку нативно.

- **Плюсы:** лучшее качество (модель видит оригинал), нет локальных
  моделей.
- **Минусы:** зависит от внешнего API и его стабильности; CDP-транспорт
  хрупок (селекторы, WAF, версии интерфейса); требует перехвата
  внутреннего запроса; приватность (изображение уходит в DeepSeek);
  сейчас нет подтверждения, что API это поддерживает.

### 2.2. Сравнение

| Критерий | A: OCR | B: LLaVA | C: CDP/native |
|---|---|---|---|
| Понимание сцены | низкое (только текст) | высокое | высокое |
| Задержка | ~0.2–1 с | ~2–10 с | зависит от DeepSeek |
| Железо | CPU | GPU/память | CPU + Chrome |
| Приватность | локально | локально | уходит в DeepSeek |
| Внешняя зависимость | Tesseract | Ollama + модель | DeepSeek API/WAF |
| Сложность | низкая | средняя | высокая |
| Риск поломки | низкий | средний | высокий |

### 2.3. Выбор: гибрид A → B (C отложен)

Выбираем **гибридную схему**:

1. **Сначала OCR (A).** Для большинства задач достаточно текста:
   прочитать сообщение об ошибке, найти подпись, распознать форму.
   Дешёво, быстро, локально.
2. **Если OCR не хватает — LLaVA (B).** Когда нужен смысл сцены
   (иконки, расположение элементов, «что изображено»), шлюз вызывает
   локальную vision-модель и получает описание.
3. **CDP/native (C) — Deferred** (R-06-03): включаем только если DeepSeek
   официально поддержит изображения и это подтвердится живым захватом.

Схема сохраняет главное преимущество текущей архитектуры: **DeepSeek
продолжает получать только текст**, поэтому клиент, PoW и SSE-слой не
меняются.

### 2.4. Поток данных (эскиз)

```text
DSH → POST /v1/chat/completions (tools=[screenshot, bash])
  → Prompt Builder (инструкция: для изображения используй screenshot)
  → DeepSeek: DSML tool_calls (screenshot / bash)
  → шлюз выполняет инструмент (или DSH — в зависимости от роли tools)
  → файл PNG на диске
  → выбор: OCR (tesseract) или LLaVA (Ollama) — по типу задачи/настройке
  → текст/описание как tool-результат
  → следующий turn DeepSeek отвечает пользователю
```

Точки интеграции: `R-06-04` (инструмент `screenshot`), Prompt Builder
(инструкция «сначала OCR, если текст; иначе описание»), конфиг шлюза
(URL Ollama, языки OCR, таймауты), `tool`-сообщения истории.

### 2.5. Fail-safe и приватность

- Если OCR/LLaVA недоступны — не падать, а вернуть понятную ошибку
  инструмента; модель должна ответить текстом с причиной.
- Скриншоты не логируются и не попадают в `docs/captures/`; временные
  файлы удаляются после обработки.
- LLaVA вызывается только по явной настройке (`VISION_PROVIDER=ollama`);
  по умолчанию — OCR или отказ.
- Изображения с экрана могут содержать токены/переписку: запрос к
  внешним сервисам (вариант C) запрещён без отдельного согласия.

### 2.6. Открытые вопросы

- Как DSH передаёт изображения в запросе — как `content`-часть или через
  инструмент? От этого зависит, нужен ли R-06-04 вообще.
- Поддерживает ли DeepSeek `ref_file_ids` для изображений (R-06-03)?
- Минимально достаточное разрешение/формат для OCR и LLaVA.
- Нужны ли языковые пакеты `rus` в базовой поставке.
- Где брать Ollama в Docker-образе (отдельный контейнер или host).
