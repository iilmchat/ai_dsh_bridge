# Roadmap AI DSH Bridge

**Версия:** 0.6.5 · **Дата:** 2026-11-18 · **Статус:** актуален
**Связанные документы:** [DESIGN.md](DESIGN.md), [DESIGN_GOOGLE.md](DESIGN_GOOGLE.md),
[DESIGN_V06_VISION.md](DESIGN_V06_VISION.md),
[KNOWN_ISSUES.md](KNOWN_ISSUES.md) (Backlog, KI-1001…KI-1022).

Карта развития фиксирует идеи, которые пока не реализованы, чтобы они не
потерялись и не дублировались в реестре проблем. Roadmap — не обещание
сроков: порядок этапов отражает зависимости и риск, а не календарь.

## Принципы

1. **Совместимость важнее фич.** Любое изменение не должно ломать
   OpenAI/SSE-контракт DSH (`tool_calls`, `id`/`name` только в первом чанке).
2. **Сначала надёжность, потом скорость.** Vision и performance — после
   стабильного сквозного цикла.
3. **Минимум внешних зависимостей.** Новый инструмент добавляется, только
   если его нельзя реализовать через `bash`/локальный HTTP.
4. **Каждая фича = код + тесты + документация + запись в реестре.**
   Идеи из этого файла ведутся как `KI-1001…` в Backlog KNOWN_ISSUES.

## v0.6.0 — Vision & Multimodal (🔴 Critical)

**Зачем.** Без зрения агент не может анализировать интерфейсы, читать
сканы PDF и текст на экране, проверять результат скриншота. Сейчас
`bash` может сохранить файл, но модель его не видит — в лучшем случае
возвращается путь.

**Результат этапа:** задача «сделай скриншот и опиши, что на экране»
выполняется от начала до конца: модель делает скриншот через `bash`,
изображение уходит в DeepSeek нативно (`upload_file` + `ref_file_ids`),
а OCR остаётся fallback'ом для текста на экране.
**Статус:** **Done** (0.6.1). S1 (`screenshot`) и S2 (OCR) закрыты в
0.6.0-alpha, S3 (`ref_file_ids`) — в 0.6.1; S4 (LLaVA) переведён в
`Deferred`, R-06-04 — в `Won't Fix` (см. ниже).

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-06-01 | OCR (Tesseract) | 🔴 Critical | Done | Fallback для «зрения» без vision-модели: модель через `bash` запускает `tesseract screenshot.png stdout` и получает текст. Работает локально, быстро, только текст. Реализовано в 0.6.0-alpha (S2): few-shot в Prompt Builder, полный путь к `tesseract` + подсказка `where tesseract`. |
| R-06-02 | Локальная vision-модель (Ollama/LLaVA) | 🟠 High | Deferred | Агент делает скриншот, отправляет в LLaVA через локальный HTTP, получает описание и использует его в ответе. **Причина отсрочки (2026-10-20):** S3 даёт нативное зрение веб-модели — изображение уходит через `ref_file_ids`, поэтому отдельная vision-модель дублирует штатный путь и требует GPU/памяти. **Условие пересмотра:** если DeepSeek перестанет принимать изображения или понадобится офлайн-анализ без отправки экрана в облако. |
| R-06-03 | Изображения через `upload_file` + `ref_file_ids` (S3) | 🟠 High | Done 2026-10-20 | `data:image/...;base64,...` и http(s)-URL загружаются в DeepSeek (`POST /api/v0/file/upload_file`, PoW), шлюз ждёт `fetch_files` (PENDING → SUCCESS) и передаёт `ref_file_ids` в `chat/completion`. Реализовано в 0.6.1, KI-1003 → Fixed. |
| R-06-04 | Инструмент `screenshot` | 🟠 High | Won't Fix | Своя обёртка над `screenshot-desktop` (Node.js), сразу возвращает base64 и путь — без парсинга вывода `bash`. **Причина отказа (2026-10-20):** S1 закрыт few-shot PowerShell (`CopyFromScreen`) через `bash`, а изображения доставляются нативно (S3); отдельная обёртка добавляет зависимость и не даёт нового сценария (DESIGN_V06_VISION § 2.6). |

**Критерии готовности v0.6.0 (выполнены):** скриншот → OCR или нативная
передача изображения (`image_url` → `ref_file_ids`) → ответ модели;
живой e2e подтвердил, что модель описывает загруженную картинку; секреты
на скриншотах не логируются.

**Риски:** приватность (экран может содержать токены/переписку); качество
OCR на сложных шрифтах; лимиты DeepSeek на размер/тип изображения.

## v0.6.2 — Google Provider (🟠 High)

**Зачем.** Шлюз был привязан к `chat.deepseek.com`, а DSH мог выбрать только
DeepSeek-модели. Нужен доступ к **Google ИИ-чату** двумя независимыми путями:
официальным API (стабильно, по ключу) и веб-чатом (без ключа, по cookie).

**Результат этапа:** DSH видит `google-gemini-api-flash`,
`google-gemini-api-pro`, `google-gemini-web`; L2 (DSML) общий, контракт
OpenAI/SSE не изменился (DESIGN_GOOGLE.md).

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-06-05 | Gemini API (официальный) | 🟠 High | Done 2026-11-18 | `GEMINI_API_KEY` → `POST /v1beta/models/{model}:generateContent` (`x-goog-api-key`), `systemInstruction` + `contents` + `generationConfig`, `thought`-части отбрасываются, usage из `usageMetadata`, маппинг ошибок 401/403/429/5xx/blockReason. |
| R-06-06 | Gemini Web (веб-чат) | 🟠 High | Done 2026-11-18 | `pnpm webauth:google` захватывает cookie `google.com` в `google-auth.json`; клиент `StreamGenerate` (`at`/`f.req`) извлекает `SNlM0e` из `/app` (кэш 5 мин) и разбирает кадры `wrb.fr`; коды 1037/1052/1060 смаплены. |
| R-06-07 | Слой провайдеров | 🟡 Medium | Done 2026-11-18 | `ChatProvider` + `ProviderNotConfiguredError`/`ProviderRequestError`, реестр `PROVIDER_MODELS`, роутинг по `model` в `/v1/chat/completions`; `GET /v1/models` строится из реестра. |

**Критерии готовности (выполнены):** запрос к Google-модели проходит тот же
L2-цикл (`tools` → DSML → `tool_calls`), ошибки возвращаются в
OpenAI-формате, `pnpm typecheck/lint/test/build` зелёные (168 тестов), живая
проверка возможна после `GEMINI_API_KEY`/`webauth:google`.

**Риски:** веб-протокол неофициальный и не проверен на живом аккаунте
(KI-1017, KI-1019); изображения Google-провайдерам пока не передаются
(KI-1018); лимиты бесплатного аккаунта Google.

## v0.6.3 — Google Expansion (🟠 High)

**Зачем.** После живой проверки веб-провайдера (0.6.3) расширить Google:
дать API изображения и добавить выбор модели в веб-чате.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-06-08 | Изображения в Gemini API | 🟠 High | Done 2026-11-18 | `image_url` (`data:base64`/http) → `inlineData` (`mimeType` + base64) в `contents[].parts[]` рядом с текстом; лимит 10 МиБ; KI-1018 закрыт для API, веб-часть открыта. |
| R-06-09 | Выбор модели Gemini Web | 🟡 Medium | Done 2026-11-18 | Модели `google-gemini-web-flash`/`-pro`; заголовок `x-goog-ext-525001261-jspb` подставляется по `upstreamModel`; живой e2e подтвердил flash (8.7 с) и pro (15.0 с). |
| R-06-10 | Лимит заголовков Google + живой e2e | 🟠 High | Done 2026-11-18 | Google отдаёт ~30 КБ заголовков: `fetch` падал `HeadersOverflowError`, `webauth:google` не сохранял сессию. **Критерии готовности (выполнены):** `pnpm e2e:gemini` (web/flash/pro) →

`typecheck/lint/test/build` зелёные.

**Риски:** заголовки моделей Google могут смениться (KI-1019); изображения в
веб-чате не поддержаны (KI-1018); лимиты аккаунта Google.

## v0.6.4 — Google Web Vision (🟠 High)

**Зачем.** Закрыть последний функциональный пробел Google: изображения в
веб-чате `gemini.google.com`, чтобы DSH мог отправлять скриншоты и в
Gemini Web, а не только в Gemini API/DeepSeek.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-06-11 | Изображения в Gemini Web | 🟠 High | Done 2026-11-18 | `image_url` → `content-push.googleapis.com/upload` (multipart, `Push-ID`, `X-Tenant-Id`) → `messageContent = [prompt, 0, null, [[[id], имя]]]` в `StreamGenerate`; `googleRequestAsync` отправляет бинарное тело. Живой прогон: красный квадрат → «Красный». KI-1018 → Fixed. |

**Критерии готовности (выполнены):** картинка проходит путь
`/v1/chat/completions` → upload → `StreamGenerate` → ответ модели; юнит-тесты
проверяют multipart и `f.req`; 179 тестов, проверки зелёные.

**Риски:** транзиентные `Connect Timeout` к `content-push.googleapis.com`
(наблюдался один раз, повтор успешен — ретрай не реализован); лимиты
аккаунта Google.

## v0.7.0 — Performance & Reliability (🟠 High)

**Зачем.** Сквозной цикл работает, но PoW добавляет ~500 мс, а SSE
начинается только после полного ответа DeepSeek; при истечении сессии
нужен ручной `pnpm webauth`.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-07-01 | PoW через `worker_threads` | 🟠 High | Planned | Параллельный перебор nonce по ядрам: цель ~150 мс вместо ~500 мс (KI-014). |
| R-07-02 | Инкрементальный streaming DSML | 🟠 High | Planned | Потоковый tokenizer: первый SSE-чанк до завершения ответа DeepSeek, а не после буферизации. Требует fail-safe на незакрытых блоках. |
| R-07-03 | Ротация/пересоздание `chat_session_id` | 🟠 High | Planned | Автоматически пересоздавать сессию при 401/истечении, чтобы не требовать ручного `pnpm webauth`. |
| R-07-04 | Мультиаккаунтность | 🟡 Medium | Planned | Несколько `auth.json`, балансировка и fallback между аккаунтами. |

**Критерии готовности v0.7.0:** PoW-бенчмарк <200 мс; первый SSE-байт
<1 c для коротких ответов; при 401 сессия пересоздаётся без рестарта.

## Зависимости и порядок

```text
v0.6.0: R-06-01 (OCR) + R-06-03 (ref_file_ids) ──> Done
        R-06-02 (LLaVA) — Deferred, R-06-04 (screenshot tool) — Won't Fix
v0.6.2: R-06-07 (реестр/контракт провайдеров) → R-06-05 (Gemini API);
        R-06-06 (Gemini Web) зависит от веб-протокола Google (KI-1017/1019).
v0.6.3: R-06-10 (лимит заголовков) разблокировал живую проверку R-06-06;
        R-06-08 (изображения API) и R-06-09 (flash/pro) — после неё.
v0.6.4: R-06-11 (изображения Web) использует upload из R-06-06.
v0.7.0: R-07-01 (PoW) независим; R-07-02 (streaming) зависит от
        текущего DSML-парсера и SSE-writer; R-07-03 — от клиента DeepSeek.
v0.8.0: R-08-01/02 — упаковка; R-08-03 — prompt/модель; R-08-04 — метрики.
v0.9.0: R-09-01 внешне зависим (WAF); R-09-02 — от изменений DeepSeek.
```

**Почему такой порядок:** v0.6 закрывает главный функциональный пробел
(агент не видит экран); v0.7 улучшает уже работающий цикл, не меняя
контракт; v0.8 нужен для распространения; v0.9 — страховки на случай
изменений внешнего API и отложенные удобства.

## Открытые вопросы

- Нужен ли OCR для не-латинских языков (rus/eng) и PDF-сканов.
- Публиковать ли npm-пакет под именем `ai-dsh-bridge` (проверить занятость).
- Как ограничивать внешние `image_url` (SSRF) — см. KI-1016.

## Правила ведения Roadmap

- ID фиксированы (`R-XX-NN`); новые идеи получают следующий свободный ID.
- Статусы: `Planned` → `In Progress` → `Done`; отказ — `Won't Fix` с
  причиной; временная заморозка — `Deferred`.
- Каждая идея дублируется в Backlog KNOWN_ISSUES (`KI-1001…`) со ссылкой
  сюда; при старте работы создаётся обычный KI с техническими деталями.
