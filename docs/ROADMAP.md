# Roadmap AI DSH Bridge

**Версия:** 0.5.5 · **Дата:** 2026-10-20 · **Статус:** draft
**Связанные документы:** [DESIGN.md](DESIGN.md), [DESIGN_V06_VISION.md](DESIGN_V06_VISION.md),
[KNOWN_ISSUES.md](KNOWN_ISSUES.md) (Backlog, KI-1001…KI-1015).

Карта развития фиксирует идеи, которые пока не реализованы, чтобы они не
потерялись и не дублировались в реестре проблем. Roadmap — не обещание
сроков: порядок этапов отражает зависимости и риск, а не календарь.

## Принципы

1. **Совместимость важнее фич.** Любое изменение не должно ломать
   OpenAI/SSE-контракт DSH (`tool_calls`, `id`/`name` только в первом чанке).
2. **Сначала надёжность, потом скорость.** Vision и performance — после
   стабильного сквозного цикла.
3. **Минимум внешних зависимостей.** Новый инструмент добавляется, только
   если его нельзя реализовать через `bash`/локальный HTTP.
4. **Каждая фича = код + тесты + документация + запись в реестре.**
   Идеи из этого файла ведутся как `KI-1001…` в Backlog KNOWN_ISSUES.

## v0.6.0 — Vision & Multimodal (🔴 Critical)

**Зачем.** Без зрения агент не может анализировать интерфейсы, читать
сканы PDF и текст на экране, проверять результат скриншота. Сейчас
`bash` может сохранить файл, но модель его не видит — в лучшем случае
возвращается путь.

**Результат этапа:** задача «сделай скриншот и опиши, что на экране»
выполняется от начала до конца; изображение проходит через OCR или
локальную vision-модель, а текст попадает в prompt DeepSeek.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-06-01 | OCR (Tesseract) | 🔴 Critical | Planned | Fallback для «зрения» без vision-модели: модель через `bash` запускает `tesseract screenshot.png stdout` и получает текст. Работает локально, быстро, только текст. |
| R-06-02 | Локальная vision-модель (Ollama/LLaVA) | 🟠 High | Planned | Агент делает скриншот, отправляет в LLaVA через локальный HTTP, получает описание и использует его в ответе. Нужны GPU/память и модель. |
| R-06-03 | Base64-картинки в DeepSeek Web | 🟡 Medium | Deferred | Через CDP-fallback, если DeepSeek Web API начнёт поддерживать `ref_file_ids` для изображений. Зависит от внешнего API. |
| R-06-04 | Инструмент `screenshot` | 🟠 High | Planned | Своя обёртка над `screenshot-desktop` (Node.js), сразу возвращает base64 и путь — без парсинга вывода `bash`. |

**Критерии готовности v0.6.0:** скриншот → OCR/LLaVA → текст в prompt;
тест на mock vision-провайдера; документация и `DESIGN_V06_VISION.md`
переведены из черновика в актуальный DESIGN; секреты на скриншотах не
логируются.

**Риски:** приватность (экран может содержать токены/переписку); качество
OCR на сложных шрифтах; требования LLaVA к железу; задержка >5 c.

## v0.7.0 — Performance & Reliability (🟠 High)

**Зачем.** Сквозной цикл работает, но PoW добавляет ~500 мс, а SSE
начинается только после полного ответа DeepSeek; при истечении сессии
нужен ручной `pnpm webauth`.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-07-01 | PoW через `worker_threads` | 🟠 High | Planned | Параллельный перебор nonce по ядрам: цель ~150 мс вместо ~500 мс (KI-014). |
| R-07-02 | Инкрементальный streaming DSML | 🟠 High | Planned | Потоковый tokenizer: первый SSE-чанк до завершения ответа DeepSeek, а не после буферизации. Требует fail-safe на незакрытых блоках. |
| R-07-03 | Ротация/пересоздание `chat_session_id` | 🟠 High | Planned | Автоматически пересоздавать сессию при 401/истечении, чтобы не требовать ручного `pnpm webauth`. |
| R-07-04 | Мультиаккаунтность | 🟡 Medium | Planned | Несколько `auth.json`, балансировка и fallback между аккаунтами. |

**Критерии готовности v0.7.0:** PoW-бенчмарк <200 мс; первый SSE-байт
<1 c для коротких ответов; при 401 сессия пересоздаётся без рестарта.

## v0.8.0 — Ecosystem (🟡 Medium)

**Зачем.** Проект должен быть удобен вне текущей машины: установка без
клонирования, запуск в контейнере, режим reasoner и наблюдаемость.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-08-01 | Публикация в npm | 🟡 Medium | Planned | `npx ai-dsh-bridge` без клонирования; публичный пакет и версии. |
| R-08-02 | Docker-образ | 🟡 Medium | Planned | `docker run -p 3456:3456` (плюс том для `auth.json`); образ без секретов. |
| R-08-03 | Поддержка `deepseek-web-reasoner` | 🟡 Medium | Planned | Сейчас ответы обрезаются по токенам из-за долгих рассуждений; решение — ограничить `max_tokens` в промпте/инструкция «не рассуждай долго». |
| R-08-04 | Метрики и OTel | 🟡 Medium | Planned | Токены, время ответа, время PoW, число tool_calls; экспорт в OTel. |

**Критерии готовности v0.8.0:** `npx`/Docker-запуск по README; reasoner
не обрезается на тестовом сценарии; метрики доступны локально.

## v0.9.0 — Advanced (🟢 Low, Deferred)

**Зачем.** Долгосрочная устойчивость к изменениям DeepSeek и удобство
настройки. Эти задачи отложены: текущий прямой HTTP-транспорт и
`DeepSeekHashV1` работают, а стоимость реализации высока.

| ID | Фича | Приоритет | Статус | Описание |
|---|---|---|---|---|
| R-09-01 | CDP-fallback | 🟢 Low | Deferred | Если прямые HTTP-запросы перестанут работать из-за WAF, управлять DeepSeek через Chrome DevTools Protocol (в стиле `webauth`). |
| R-09-02 | Автообновление PoW-алгоритма | 🟢 Low | Deferred | Если DeepSeek сменит `DeepSeekHashV1`, быстро адаптировать решатель (конфиг/плагин/загрузка новой реализации). |
| R-09-03 | Web UI настройки | 🟢 Low | Deferred | Замена `pnpm webauth` на локальный веб-интерфейс (вход, статус сессии, логи). |

## Зависимости и порядок

```text
R-06-04 (screenshot tool) ─┬─> R-06-01 (OCR) ──> v0.6.0
                           └─> R-06-02 (LLaVA) ─┘
v0.7.0: R-07-01 (PoW) независим; R-07-02 (streaming) зависит от
        текущего DSML-парсера и SSE-writer; R-07-03 — от клиента DeepSeek.
v0.8.0: R-08-01/02 — упаковка; R-08-03 — prompt/модель; R-08-04 — метрики.
v0.9.0: R-09-01 внешне зависим (WAF); R-09-02 — от изменений DeepSeek.
```

**Почему такой порядок:** v0.6 закрывает главный функциональный пробел
(агент не видит экран); v0.7 улучшает уже работающий цикл, не меняя
контракт; v0.8 нужен для распространения; v0.9 — страховки на случай
изменений внешнего API и отложенные удобства.

## Открытые вопросы

- Поддерживает ли DeepSeek Web приём изображений (`ref_file_ids`) — от
  этого зависит R-06-03.
- Как DSH передаёт изображения в запросе: через `content`-массив или
  отдельный инструмент — влияет на R-06-04.
- Нужен ли OCR для не-латинских языков (rus/eng) и PDF-сканов.
- Публиковать ли npm-пакет под именем `ai-dsh-bridge` (проверить занятость).
- GPU-бюджет для LLaVA: локальная машина или внешний сервер.

## Правила ведения Roadmap

- ID фиксированы (`R-XX-NN`); новые идеи получают следующий свободный ID.
- Статусы: `Planned` → `In Progress` → `Done`; отказ — `Won't Fix` с
  причиной; временная заморозка — `Deferred`.
- Каждая идея дублируется в Backlog KNOWN_ISSUES (`KI-1001…`) со ссылкой
  сюда; при старте работы создаётся обычный KI с техническими деталями.
